## B1 caveat (read before judging any result below)

Per board blocker B1, `ai/photo_analyzer/input/` has no real photo sets —
personal photos are gitignored and have not been supplied by the user yet.
All 4 test cases below therefore run on **SYNTHETIC photo sets** (template
renders of the meta/realistic base, generated by `ai-pipeline` the same way
the calibration loop does). This validates the *pipeline plumbing*
(photos → params → meta mapping → assembled GLB → sandbox) but **not**
real-world identity/appearance fidelity — a synthetic "photo" is a render of
the very template the pipeline maps back onto, so identity-match scores are
expected to look artificially strong. Judge PASS/FAIL here as "did the
mechanism work correctly", not "does this generalize to real photos". The
"ready for real photos?" verdict at the end addresses that distinction
explicitly.

## Method (per case)

1. Run the backend CLI with the case's params JSON (`--skip-analysis`),
   requesting the case's assets via `--assets '<json>'` (confirmed
   mechanism — see T5 section below).
2. `verify_glb.py <avatar.glb> <preview.png>` — check bone count (expect 101),
   morph target count (expect ~148+ animation keys after identity bake),
   mesh list, material/texture completeness, no import errors.
3. Compare the case's preview render against
   `meta_avatar/blender/morphs/baseline_{male,female}/neutral_front.png` —
   visual check that the baked face differs from neutral in the direction
   the params specify (e.g. wider jaw, bigger eyes per exaggeration).
4. Check the GLB mesh list for the requested asset meshes (hair/beard/
   glasses/hat/clothing) and eyeball the preview render for gross clipping.
5. Confirm ARKit/animation shape keys are present (from `verify_glb.py`
   output) and the skeleton is intact (101 bones, `CC_Base_*` names).
6. Note whether the identity direction survived pipeline → meta mapping →
   exaggeration (synthetic-photo caveat applies — see above).

## Fix round (T8/T9) — 2026-07-22

### Root cause (T8)

Diagnosed as an **axis-frame mismatch**, not a fit-value problem per se: the
catalog's `styles.meta.offset` is authored/stored in three.js/glTF frame
(Y=up) for the runtime `WardrobeManager`, but `assemble_avatar.py` (the
Blender-side assembly step) was adding that vector unconverted as a Blender
translation (Z=up) — e.g. cap's catalog offset `[0, -0.033461, -0.006164]`
(three.js) was applied as Blender `(Y=-0.033461, Z=-0.006164)` instead of
the correct Blender `(Y=0.006164, Z=-0.033461)`, putting ~90% of the
intended downward correction into the wrong axis. Separately,
`attach_skinned()` (used for `beard_short`, `attach_type: "skinned"`) took
no offset/scale parameters at all — the catalog's fit values for skinned
items were computed by `resolve_assets()` but silently never read at
assembly time, so the beard kept whatever position its realistic-rig
vertex data encoded, landing at eye/brow height on the Meta armature.

### T8 fix, independently read and verified (T9)

I read `meta_avatar/blender/scripts/assemble_avatar.py` in full myself
(only file changed, confirmed via `git status`/directory listing — no other
pipeline file touched). Confirmed present:

- `_meta_offset_to_blender(offset)` (lines 89–114): converts a three.js-frame
  offset `(x,y,z)` to Blender frame via `(x, -z, y)`. I sanity-checked this
  against `meta_avatar/blender/scripts/compute_fits.py`'s `to_threejs()`
  (line 52-54: `x,y,z = offset_blender; return [x, z, -y]`) by inverting it
  algebraically: given threejs `(X,Y,Z) = (x_b, z_b, -y_b)`, solving for
  Blender `(x_b,y_b,z_b)` gives `(X, -Z, Y)` — **exactly** what
  `_meta_offset_to_blender` computes. Round-tripped the cap example from the
  function's own docstring (`[0,-0.033461,-0.006164]` → Blender
  `(0, 0.006164, -0.033461)` → back through `to_threejs` → `[0, -0.033461,
  -0.006164]`) by hand — closes exactly. **The conversion math is correct.**
- `attach_bone()` (line 140): now calls `_meta_offset_to_blender(offset)`
  before adding it to `head_world`. Confirmed by reading the call site.
- `attach_skinned()` (line 177): now accepts `offset`/`scale` params, scales
  the mesh's own vertex data about its local origin, then translates by the
  axis-converted world-space offset — **before** the armature retarget/
  reparent (so the meta armature's own 0.01 import scale can't distort it,
  same reasoning `attach_bone()` already used). Confirmed by reading the
  function body (lines 177–239) and its call in `main` (line 292-294,
  `entry.get("offset")`/`entry.get("scale")` now passed through — previously
  `attach_skinned()` took only `(obj, dup_arm, item_id)`, no fit params at
  all, confirming the D6 root cause as described).
- No fit VALUES in `assets/shared/catalog.json` were changed — confirmed by
  diffing the case manifests: `case1_fix`'s beard/glasses/hair `offset`/
  `scale` fields are numerically identical to what T3 originally published
  (`beard_short`: offset `[0,-0.135,0.05]`, scale `1.0294`; `glasses_round`:
  offset `[0,-0.011711,-0.002158]`, scale `1.447`; `cap`: offset
  `[0,-0.033461,-0.006164]`, scale `1.447`).

## D3 — bone-attached per-style offset undershoot (found T3, fixed T6) — VERIFIED RESOLVED

Orchestrator relayed: hair-assets (T3) found that bone-attached per-style
`offset`/`scale` overrides landed ~100x undershot (a requested 0.05m offset
moved the asset ~0.0005m in world space, with some axis mixing), because the
original `wardrobe.js` applied the offset as a post-hoc mutation of
`attachment.root.position` — which lands in the bone's local frame (scaled
by the armature's ~0.01 import scale and rotated by the bone's rest
orientation), not world meters. Sandbox (T6) fixed it by folding offset/scale
into `viewer.js`'s `attachAsset()` matrix construction itself, before the
bone's inverse rest transform is applied (skinned items are unaffected — their
holder parents to the identity-transform avatar root, so a post-hoc nudge was
already correct there).

**Independently re-verified, not just re-stated:**
- Read `viewer.js` `attachAsset(url, name, boneName, offset, scale)` (lines
  ~281-312): offset is added to the bone's *world* position before
  `parentInv` is computed and multiplied in, so the inverse-rest-transform
  cancels correctly — confirmed this is the right fix for the described bug.
- Read `wardrobe.js`'s current `equip()`: bone-attached items now pass
  `fit?.offset`/`fit?.scale` straight into `viewer.attachAsset(...)`; only
  *skinned* items still use the post-hoc `_applyFitPostHoc()` path (correct,
  per the comment, since their holder has no rest-transform to cancel).
- **Ran my own live numeric test** (not the orchestrator's numbers) in the
  sandbox console: attached `wardrobe/hats/cap/cap.glb` to `CC_Base_Head`
  twice, once with no offset and once with `offset=[0,0.05,0]`, then read
  each attachment's `matrixWorld` translation directly. Result: world-space
  delta = `[0, 0.05000000000000027, 0]`, length `0.05m` — exactly the
  requested offset, zero axis mixing (previously would have been ~100x
  smaller and axis-mixed by the bone's rest rotation).
- **Visual confirmation**: screenshotted both test caps live on the
  Realistic male head — two caps stacked with a clean, evenly-spaced 0.05m
  vertical gap, both axis-aligned (no tilt/skew), matching the numeric
  result. Screenshot not saved as a file (console-driven test, cleaned up
  after — no `styles.meta` offset entries exist in the catalog yet since
  hair-assets hasn't published fitted hair/beard/glasses/hats items, so this
  was a synthetic offset test of the fixed mechanism, not a real catalog item).

**Verdict:** D3 is a confirmed real defect that was found and fixed
in-phase, and the fix itself checks out under independent re-verification
(code read + live numeric test + visual). Recording as **found-and-resolved**,
not just "reported resolved." Credit: cross-agent empirical repro
(hair-assets found it while testing a real fit) → ownership-respecting
handoff (hair-assets didn't patch sandbox's file themselves) → numeric
