# Avatar Asset System

Modular wardrobe architecture: assets are equipped/removed at runtime without
ever modifying the base mesh. One generic engine serves every category — there
is deliberately **no** per-category HairManager/BeardManager/... class
hierarchy; categories are *data*.

## The two attachment types (this is the whole system)

| `attach_type` | Used by | Mechanism |
|---|---|---|
| `bone` | glasses, hats, watch, earrings, necklace, backpack | Rigid mesh authored **relative to its attach bone** (meters, glTF Y-up, avatar faces +Z). Runtime parents it to that bone at unit scale (`SandboxViewer.attachAsset` bakes the inverse bone transform). Follows the bone rigidly. |
| `skinned` | hair, beard, eyebrows, tops, pants, shoes | Mesh skinned to the **CC3+ skeleton** (standard bone names). Runtime re-binds every skinned mesh to the *avatar's own bones by name* (`SandboxViewer.attachSkinned`) and discards the asset's armature copy. Deforms with the body. |

Because all CC3+ characters share one skeleton and bone naming, a skinned
asset built once binds to the male, the female — and later any stylized base
that keeps the naming. **That is the reuse contract for future styles.**

## Runtime: `WardrobeManager` (frontend/threejs-viewer/src/wardrobe.js)

- `init()` loads `wardrobe/catalog.json`
- `equip(slot, itemId | null)` — one item per slot; equipping replaces, `null` removes
- `setColor(slot, hex)` — tints the materials listed in the item's `colorable_materials`
- `reapply()` — re-equips the whole outfit after an avatar GLB swap
- `state()` — serializable outfit (`{slot: {item, color}}`), the future
  `appearance` section of the avatar params JSON

Slots (`hair`, `beard`, `eyebrows`, `glasses`, `hat`, `top`, `pants`,
`shoes`, `wrist`, `ears`, `neck`, `back`) are defined in the catalog with a
label, sandbox tab, and optional color palette — adding a category is a
catalog edit, not a code change.

## Folder structure & metadata

```
assets/shared/
├── catalog.json                  # aggregated: palettes, slots, items
├── hair/<id>/                    #   ── one folder per item ──
│   ├── <id>.glb                  # exported asset
│   ├── item.json                 # metadata (below)
│   └── thumbnail.png             # 256² auto-render for pickers
├── beards/…  eyebrows/…  glasses/…  hats/…
├── clothes/…                     # tops + pants
├── shoes/…
└── accessories/…                 # watch, earrings, necklace, backpack
```

`item.json`:
```json
{
  "id": "tshirt", "label": "T-Shirt", "slot": "top",
  "category_dir": "clothes", "attach_type": "skinned", "attach_to": null,
  "colorable_materials": ["tshirt_mat"],
  "file": "clothes/tshirt/tshirt.glb", "thumb": "clothes/tshirt/thumbnail.png"
}
```

Naming conventions: item ids are `snake_case` and globally unique; the
colorable material is always `<id>_mat`; `attach_to` uses CC bone names
(`CC_Base_Head`, `CC_Base_L_Hand`, ...).

The sandbox serves a copy of this tree at
`frontend/threejs-viewer/public/wardrobe/` (the build script writes both).

## Authoring & export pipeline

The demo library (22 items) is generated by
`blender/scripts/build_demo_assets.py` — fully deterministic, no AI meshes:

- **Skinned items are shells extracted from the body mesh itself**: select a
  region via skinning-weight masks (e.g. shirt = spine+clavicle+upper-arm
  weights) plus geometric landmarks, offset along normals, solidify. Because
  the shell keeps the body's vertex groups and armature, it is perfectly
  fitted and perfectly weighted for free, and the base mesh is never touched.
- **Rigid items are primitives** placed from bone/landmark positions
  (earlobe vertices for earrings, wrist-axis for the watch, scalp crown for
  hats), then recentered relative to their attach bone.
- The script exports every GLB, renders every thumbnail, writes every
  `item.json` and the aggregated `catalog.json`, and copies the tree into the
  sandbox. One command rebuilds the entire library:

```bash
blender --background --python blender/scripts/build_demo_assets.py -- \
  blender/templates/male_base.blend assets/shared \
  frontend/threejs-viewer/public/wardrobe
```

### Strand-clump hair (`build_hair_style.py`)

The shell-based hair above reads as a helmet, so proper hairstyles are
generated separately by `blender/scripts/build_hair_style.py`. Instead of
inflating the scalp it grows tapered, wavy clump tubes rooted on the scalp
(Poisson-sampled, jittered off the vertex grid), combs each one along a
per-region flow field (front / top / side / back), and keeps it hugging the
skull with a nearest-surface constraint that both pushes strands out of the
head and attracts them back when they'd fly off the skull's curvature. A thin
scalp under-shell hides skin between clumps. Styles are pure data in the
script's `STYLES` dict; each run exports one style, merges it into the
existing `catalog.json` (no full-library rebuild), and renders front /
three-quarter / side / back verification previews of the hair on the head:

```bash
blender --background --python blender/scripts/build_hair_style.py -- \
  blender/templates/male_base.blend assets/shared \
  frontend/threejs-viewer/public/wardrobe hair_swept <preview_dir>
```

**Adding a hand-authored asset** (the production path): model it in Blender —
skinned to the CC skeleton for deformables, or bone-relative for rigid items
— export a GLB into `assets/shared/<category>/<id>/`, add `item.json` +
`thumbnail.png`, append the item to `catalog.json`, re-copy to the sandbox.
Keep the source `.blend` next to the GLB for hand-authored items.

## Sandbox integration

Three tabs (Appearance / Clothing / Accessories) are generated from the
catalog's slot→tab assignments: thumbnail grid per slot with a "None" tile,
color swatch row for palette-bearing slots. Equip/swap is instant; outfits
survive avatar switches (`reapply`); "Download GLB" in the Export tab
includes everything currently equipped. `window.sandbox.wardrobe` is exposed
for console scripting.

## How stylized avatars will reuse this

1. Same skeleton + bone names → skinned assets bind unchanged; rigid assets
   attach unchanged.
2. Where a style needs its own look, `item.json` gains a per-style variant
   file (see `docs/architecture_v2_proposal.md` §1) — same id, same slot,
   different GLB. The manager resolves style variant → default.
3. `WardrobeManager` itself never changes: it is already 100% catalog-driven.

## Known limitations (accepted for the demo library)

- Demo shells are **male-fitted**; on the female base they attach and deform
  correctly but sit oversized (visible on the head). Production assets get
  per-gender GLBs via the `variants` mechanism.
- Identity morphs (e.g. `face_width`) do not deform equipped assets — shells
  are static copies of the neutral shape. Production fix: bake matching
  morph deltas into asset shells at authoring time (same masks, same script).
- Hats are oversized rather than hiding hair; a `hides: ["hair"]` slot rule
  is the clean future mechanism if needed.
- Small stray fragments near the sideburns on hair masks; cosmetic only.
